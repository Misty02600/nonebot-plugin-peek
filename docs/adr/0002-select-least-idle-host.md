# ADR-0002：按空闲时间选择多主机

## 状态

已采纳

## 日期

2026-02-10

## 当时遇到了什么

同一个机器人可能连接多台运行 PeekAPI 的电脑。用户期望截图或录音来自最近实际使用的设备，而不是每次
手动指定主机，同时单主机配置不应承担额外探测开销。

## 最后决定

- 使用有序的 `PEEK_HOSTS` 列表配置一个或多个 PeekAPI 地址，所有客户端共享插件级 API Key、超时和重试设置。
- 单客户端时直接选用；多客户端时并发请求 `/idle`，选择 `idle_seconds` 最小的主机。
- 无主机成功返回空闲信息时，确定性地回退到配置列表第一项，让后续正常请求与错误处理决定用户可见结果。

## 为什么这样选

空闲时间直接反映各设备最近的用户输入，比轮询或随机选择更符合“当前正在使用的电脑”。并发探测避免
主机数量线性增加等待时间，固定的第一项回退则保留了可预测的默认目标。

## 没有采用的方案

- 始终请求第一台主机：兼容简单，但无法自动跟随当前使用设备。
- 轮询或随机选择：能分散请求，却与用户活动状态无关。
- 所有 `/idle` 请求失败时直接拒绝命令：故障更明确，但会放弃第一台主机仍可提供截图或录音的机会。

## 带来的影响

- 有利：多设备场景无需增加命令参数，单主机场景没有额外 `/idle` 请求。
- 代价：多主机命令在业务请求前增加一次最多约 5 秒的探测阶段。
- 风险：PeekAPI 的 `/idle` 语义或可用性异常时可能选错主机；全部探测失败时仍会额外等待第一台业务请求。
